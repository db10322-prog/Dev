# 모바일 확장 설계 문서 (T-10, 구현 없음 — 설계만)

발표 슬라이드에 그대로 붙일 수 있는 형태로 정리.

## 왜 데스크톱과 다른가

데스크톱 버전의 핵심 트릭은 "크롬 확장이 현재 탭 DOM에서 이미 렌더링된 본문/댓글을 읽는다"는 것이다. 모바일에서는 이 전제가 무너진다.

- **안드로이드**: `SYSTEM_ALERT_WINDOW` 권한으로 떠있는 버블(오버레이 위젯)은 구현 가능하다. 하지만 그 버블에서 **다른 앱(브라우저/뉴스 앱)의 DOM에 접근할 방법이 없다.** 따라서 데스크톱처럼 "현재 보고 있는 화면"을 그대로 읽는 구조는 불가능하고, 공유 시트(Share Intent)로 URL을 받아 **서버가 직접 그 URL을 fetch**하는 경로로 바꿔야 한다. 원 설계 문서에서 이미 지적했듯 서버 fetch는 봇 차단·동적 렌더링 때문에 성공률이 데스크톱 DOM 추출보다 낮다.
- **iOS**: 다른 앱 위에 떠 있는 오버레이 UI 자체가 OS 정책상 금지된다(Apple은 시스템 전역 오버레이를 허용하지 않음). 따라서 "바탕화면 캐릭터가 떠 있다가 클릭하면 분석" UX를 iOS에서 재현하는 것은 원천적으로 불가능하다. 유일한 현실적 경로는 **Share Extension**(뉴스 앱/Safari에서 "공유" → 이 앱으로 전달) + **앱 내 결과 화면**이다.

## 플랫폼별 기능 대조표

| 기능 | 데스크톱(Windows, 현재 구현) | 안드로이드(설계만) | iOS(설계만) |
| :--- | :--- | :--- | :--- |
| 상시 캐릭터 오버레이 | 가능 (Electron alwaysOnTop) | 가능 (`SYSTEM_ALERT_WINDOW`) | **불가능** (OS 정책) |
| 현재 화면 본문 자동 추출 | 가능 (크롬 확장 DOM 접근) | **불가능** (타 앱 DOM 접근 불가) | **불가능** (동일) |
| 기사 전달 방식 | 크롬 확장 → 네이티브 메시징 | 공유 시트(Share Intent) → URL | Share Extension → URL |
| 본문 확보 방식 | 브라우저가 렌더링한 DOM 그대로 | 서버가 URL fetch (성공률 낮음) | 서버가 URL fetch (성공률 낮음) |
| 댓글 수집 | 크롬 확장이 댓글 DOM 파싱 | 사실상 불가 (동일 이유) | 사실상 불가 (동일 이유) |
| 결과 표시 | Electron 결과 창 | 앱 내 화면 | 앱 내 화면 |
| 백그라운드 상시 대기 | Electron 프로세스 상시 실행 | 배터리 최적화 정책과 충돌 가능 | 해당 없음(오버레이 자체가 없음) |

## 결론

- 안드로이드는 "공유 시트 + 서버 fetch" 구조로 **축소된 버전**을 만들 수 있으나, 데스크톱 대비 본문 확보 성공률이 떨어진다는 한계를 반드시 명시해야 한다.
- iOS는 데스크톱과 같은 UX(바탕화면 캐릭터)를 원천적으로 재현할 수 없다. Share Extension 기반의 "다른 앱" 경험으로 설계를 완전히 바꿔야 한다.
- 이번 대회/데모의 범위는 Windows 데스크톱으로 한정하고, 모바일은 이 설계 문서로만 방어한다(범위 밖으로 명시됨).
